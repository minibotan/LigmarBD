# Разбор описаний умений: поля и расчёт урона

Дата анализа: 2026-09-27.

Прочитаны русские описания всех 118 умений шести классов и всех имеющихся вариантов уровней: 274 строки наблюдений, 224 пары «умение + уровень» . Для неоднозначных формулировок дополнительно сверены английские описания. Это анализ сохранённых данных, не проверка актуального сервера. Исходные шесть JSON остаются без изменений.

## Уточнение после анализа

Формулы игры: см. [ФОРМУЛЫ_ИГРЫ.md](ФОРМУЛЫ_ИГРЫ.md). Теперь известны `BaseDamage = (AttackFromGear + CharacterLevel) * (1 + WeaponMultiplier + PassiveSkills + Effects)` и формулы защиты/попадания. Ниже сохранён исходный разбор: его неопределённость о самом определении базового урона частично устранена; состав AttackFromGear и отдельные модификаторы умений ещё требуют уточнения.

## Главное решение по структуре

Нужен массив компонентов и эффектов, а не единственное поле damage. Одно умение может одновременно наносить физический удар, накладывать магический DOT, снижать защиту цели и ухудшать собственные параметры.

Оставить существующие skill_id, skill_level, context, variant, raw_definition. Новое поле derived должно быть отдельным слоем интерпретации. Для каждого вычисленного значения хранить status: description / confirmed / observed / assumption / unresolved. Ноль означает отсутствие компонента **в описательной модели**, null — неизвестное значение. Отсутствие упоминания не доказывает отсутствие скрытой серверной механики.

## Какие поля добавить

| Поле | Содержимое и применение |

| damage_components[].delivery | direct, dot, periodic_direct, on_attack_proc; не смешивать DOT и повторяющиеся полноценные удары |

| damage_components[].trigger | on_cast_complete, on_hit, on_attack, periodic. Условия срабатывания хранить отдельно от величины |
| damage_components[].timing | duration_ms, interval_ms, tick_count, first_tick_offset_ms; отдельно периодичность из описания и из общего правила |
| damage_components[].crit_policy | default_direct, never, unresolved; DOT — never , триггерные добавки отдельно не проверены |
| damage_components[].mitigation_policy | armor, resistance, bypass_armor_resistance, unresolved. Общие процентные снижения — отдельный слой |

| effect_components[].stat, operation, value | flat_add, percent_add, set, percent_of_source; отдельно move_speed, attack_speed, cast_time, accuracy, evasion, hp_max, etc. |
| effect_components[].duration_ms | Своя длительность каждого эффекта; не одна общая длительность умения |
| effect_components[].application_order | before_damage / after_damage / unresolved. Важно для снижения защиты собственным ударом |
| stacking | family_id, replace_same_skill, replace_any_rank, coexist_other_skills; для DOT известны общие правила; не переносить их автоматически на все баффы |

| additional_cost | hp_current_fraction, mana_per_absorbed_damage и т. п. Не смешивать с обычным mana_cost каста |

Существующие range и targets уже есть — новые поля-дубликаты не нужны. Но range определяет проверку бега, а не тип урона: у мага «Сверхновая» и «Чародейский обстрел» имеют melee. Для умений это 50% уклонения бегом, а не 25%, если нет исключений. У стража «Удар по коленям» в исходных данных ranged: не исправлять по названию. Применимость проверки бега к каждому повтору обстрела требует проверки, поскольку это не обычный одиночный каст.

## Расчёт урона: сначала описание, затем механика боя

Обозначения:

- Bp, Bm — именно базовый физический/магический урон в терминах описания.
- Gp, Gm — физический/магический урон от снаряжения в терминах описания.
- Wm — магический урон от оружия. Не приравнивать Wm к Gm без подтверждения.
- F — фиксированный урон конкретного действующего уровня.
- P(x), M(x) — разовый физический/магический пакет x **до защиты, критов и проверки попадания**. U — тип не определён.
- DOTp(T,d), DOTm(T,d) — заявленная общая сумма T за d секунд, не урон одного тика.

Для обычного компонента описательная формула:

`D_description = coefficient_base * B + coefficient_gear * G + flat_damage`.

Коэффициент базы обычно 1 там, где прямо сказано «базовый урон». Если упомянут только фиксированный урон или процент снаряжения, базу не добавляем. «200% от снаряжения» — слагаемое 2·G, а не множитель 2 ко всему умению.

**Не подставлять автоматически итоговую атаку из окна персонажа вместо B.** Она может уже содержать снаряжение и баффы. Нужна привязка B/G к действующей формуле атаки и точкам применения пассивок/баффов. Описания этого не определяют. В этой работе формулы атаки/защиты не переопределялись и не проверялись заново; ниже они представлены внешними функциями. Иначе есть риск дважды посчитать снаряжение или умножить фиксированную часть не тем баффом.

### Попадание, крит и защита

Для одного разового компонента при фиксированном состоянии цели можно записать модель:

`E[D_i] = p_land_i * mean(D_precrit_i) * (1 + crit_chance_i * (crit_multiplier_i - 1)) * mitigation_i`.

Это сокращение пригодно, если защита действует множителем, крит не меняет другие правила, а округление пока не учитывается. При иных правилах считать каждую ветку отдельно. Среднее min/max брать как полусумму только при принятой симметричной модели разброса; распределение и зависимость бросков B/G описания не задают.

`D_precrit_i` — описательный компонент после корректного применения атакующих модификаторов; их порядок пока нельзя восстановить только по тексту. Для физической и магической частей смешанного удара применять разные функции защиты. Не складывать их до снижения урона одним защитным статом.

Для обычных умений мага/жреца p_ordinary=1, даже если урон физический («Стрела веры»). Для остальных — существующая функция меткости/уклонения. Бег проверяется по состоянию **в момент попадания**: у дальнего умения p_pass_running=0.75, у ближнего 0.50. У автоатак другие значения (0.50 / 0.25); type=attack в JSON означает атакующее умение, а не автоатаку.

Если отдельные проверки реализованы как независимые или с фиксированной условной вероятностью на каждом этапе, `p_land = p_ordinary * p_pass_running * p_pass_special`. Сам факт отдельной проверки не доказывает независимость: совместное действие бега и «Ловкости хищника» ещё не проверено. Порядок и обход проверок умениями с «не промахивается»/«нельзя уклониться» оставить настраиваемыми.

База КШ=1%, КУ=2.0; бонусы складываются по согласованным правилам. Каждый полный блок 20 ловкости даёт +1 процентный пункт КШ. Если берём готовый КШ персонажа, повторно базу и ловкость не добавляем. Неизвестный игровой кап КШ не выдумывать; вероятность в вычислении должна оставаться в [0,1].

### DOT

Для DOT с заявленной суммой T и длительностью d при интервале 1 с номинально N=d/1 с тиков и `tick_description=T/N`. В принятой модели тики идут на 0…N−1 секунде, а не 1…N; это наблюдалось на «Морозной чуме» и перенесено на однотипные DOT по общему допущению.

Начальный удар считается отдельно, может критовать и снижается защитой соответствующего типа. Тики не критуют, но снижаются бронёй/сопротивлением по типу урона (отдельная проверка 2026-09-29); повторно не проходят обычную проверку уклонения. Вероятность успешного наложения учитывается один раз. Действие общего процентного снижения на DOT пока лишь согласованное предположение.

Пример: «Морозная чума» уровня 8 описывает Bm сразу + 2880 за 15 с, номинально 192 за тик. Но в двух записанных боях фактический тик был 137. Поэтому **T/N — вычисление из описания, не уже проверенная формула фактического урона**. Сопротивление теперь допустимо рассматривать как причину расхождения, но без параметров цели и проверки вычисления объяснение 192 → 137 не подтверждено.

Если тот же DOT успешно обновлён, остаток старого эффекта теряется, новая версия получает свой немедленный тик и расписание. Не считать полный T за каждое применение, если эффект обновляется раньше завершения. Неуспешное новое наложение само по себе не подтверждает удаления старого DOT. Разные DOT считаются параллельно; тот же скилл другого персонажа заменяет текущий независимо от уровня.

Для одиночного успешного наложения без обновления, очищения и смерти цели: `D_total = D_initial + sum(actual_ticks)`. Для реального боя вести очередь событий тиков, замен и очищений. Включать только тики в пределах жизни эффекта и цели.

### Особые модели

- «Жертвенный взрыв»: `HP_spent = 0.60*HP_current`, `D=M(F + k*HP_spent)`. На уровне 1: M(2200 + 2.2*HP_spent). Для исходных 2000 HP до округлений расход 1200, описательный урон 4840. Это ещё не итог после баффов/защиты. Момент фиксации HP, округление и расход HP при промахе/отмене отдельно не установлены.
- «Снайперский выстрел»: `P(Bp + g(charge_time)*Gp)`. Из текста известны максимум времени и максимальный коэффициент, но не линейность g, не минимальный заряд и не то, всегда ли досрочное прерывание выпускает стрелу. Полный заряд можно описать, частичный — пока нет. Общее правило отмены бегом не подменяет специальную механику этого умения.
- «Чародейский обстрел»: повтор M(Bm+F) раз в 3 с, пока хватает маны/не отменён. Это не DOT: нельзя автоматически применять запрет критов тиков DOT к этим ударам. Также нельзя считать ВА ускорителем интервала 3 с. Неизвестны первый удар, точный ритм оплаты маны, начало отката при длительной работе и какие действия отменяют поддержание.
- «Мистический отзвук», «Зачарованные стрелы», «Завет предков»: дополнительный компонент по событию «атака». Нельзя просто навсегда прибавить процент к каждому слагаемому всех умений. Не определены подходящие триггеры (автоатака/умение/каждая цель), собственный крит, проверка попадания и взаимодействие нескольких таких эффектов.
- Умения со снижением защиты/сопротивления: считать эффект отдельно; неизвестно, снижает ли он защиту уже для своего накладывающего удара. HP-дебафф «Гнилой стрелы» не считать прямым уроном на 2% HP без подтверждения изменения текущего HP.

### DPS

Для бесконечного повторения одного простого прямого умения без маны/движения/прерываний и других задержек: `DPS_single = E[D_cast] / (cast_seconds_actual + cooldown_seconds)`. ВА уменьшает каст по принятой модели до минимума 10% исходного, не откат.

Для ротации нельзя суммировать такие DPS: касты конкурируют за время, DOT обновляются, баффы и бег меняют состояние. Считать `sum(realized_damage_events)/fight_duration`. Для AoE расчёт отдельно по каждой попавшей цели: размер группы, радиус и максимум целей из одних категорий targets не следуют.

## Особые поля поддержки, которые легко пропустить

- «Эгида»: доля поглощённого физического урона и расход маны за единицу урона — два разных числа. На примере 74% и 1.3. Неизвестно, цена берётся с поглощённой или всей входящей величины и где стоит этап защиты. Не считать её обычным плоским щитом.
- «Ветреный купол»: ёмкость щита и время существования, без процента. Действие на DOT требует отдельной проверки.
- «Жажда крови»: лечение от нанесённого урона, а не фиксированный HOT. Нужны событие-источник, доля, ограничения по типам урона и учёт фактического/избыточного урона.
- «На волоске»: триггер смертельного урона, окно действия и восстановление доли максимального HP. Это не обычное лечение по нажатию; расходуется ли эффект после срабатывания, из текста отдельно не следует.
- «Божественное касание»: снижение потери опыта, восстановление HP и маны. Число «30 от максимального» написано без знака процента и в RU, и в EN; сохранить как unresolved_unit, а не бесшумно заменить на 30%.
- «Жажда жизни»: база мгновенных 20% здоровья не уточнена как текущая/максимальная. HOT 990 за 15 с — отдельный компонент. Частоту и первый тик HOT не выдавать за экспериментально проверенное правило DOT.
- «Дыхание жизни»: сумма фиксированной и масштабируемой части лечения за длительность. «Обновляющий луч»: мгновенное лечение с процентом от магической атаки плюс отдельный фиксированный HOT. У них разные структуры.
- «Очищение»: область снятия эффектов all_negative, а не нулевой урон. «Астральный скачок»: скрытие от противников; по названию не приписывать перемещение/расстояние телепорта.
- «Подавляющее присутствие»: в тексте «на 12 от физического урона снаряжения», единица у 12 отсутствует в обоих языках. Кандидат на масштабируемый дебафф, но коэффициент 0.12 пока не подтверждён.
- Стойки воина имеют снижение противоположной защиты вплоть до 110% в следующем определении. Нужен предел итогового стата и правило суммирования; не заменять молча на −100% и не вычислять отрицательное снижение урона по догадке.
- Скорость передвижения, скорость атаки и время активации — разные статы. «Ампутация» +50% времени активации не равна −50% скорости атаки.

## Что можно считать уже сейчас, а что мешает точному урону

Можно извлечь по каждому сохранённому уровню: явные константы/проценты, состав прямого/периодического урона, длительности, шансы контроля, ограничения состояний, потребление ресурсов и специальные условия. Получатся описательные формулы и входы для симулятора.

Для точного урона в бою не хватает прежде всего:

1. Связи B/G/W с действующей формулой персонажа и порядка применения баффов к базе, снаряжению и константе умения. Уточнение источника у «Стрелы веры», «Копья тьмы» и «Пронзающего приема».
2. Причины 192 по описанию против 137 в логах DOT; округления/среза по миру и этапа фиксации статов при наложении.
3. Семантики «никогда не промахивается» против бега/специального уклонения и правил сложения отдельных проверок.
4. Частичного заряда, поддерживаемых ударов и добавок «при каждой атаке» — их нельзя приравнять к обычным ударам одним флагом.
5. Порядка дебаффа и собственного урона, поглощения, а также неоднозначных единиц в описаниях поддержки.

Это список ограничений анализа, не возобновление допроса. Численный DPS персонажа здесь не заявляется: без этих связей точные числа были бы ложной точностью.

## Закрытые вопросы после уточнений формул

Подтверждено: скобки в формулах защиты/сопротивления округляют до ближайшего целого; у сопротивления нет финальной +1; AttackFromGear включает базу оружия, заточку, дополнительные свойства и камни. Явный процент от снаряжения в умении берётся от AttackFromGear без AttackMultiplier. Бафф мага даёт плоскую добавку `fraction * WeaponAttack`; бафф жреца добавляет fraction в AttackMultiplier. Соответствующие прежние вопросы выше закрыты. Точные формулы и границы подтверждения: [ФОРМУЛЫ_ИГРЫ.md](ФОРМУЛЫ_ИГРЫ.md).


### DOT: момент учёта брони — пока неизвестен (2026-09-29)

Влияние брони на урон DOT подтверждено; момент её учёта пока не проверен. Возможны фиксация защиты/сопротивления при наложении эффекта либо пересчёт по текущим значениям на каждом тике. Ни один вариант не считать подтверждённым. При расчёте DOT с изменяющейся бронёй требуется явно выбранное допущение; при постоянной броне варианты совпадают. Проверка: изменить защиту/сопротивление цели во время уже действующего DOT, не обновляя его, и сравнить тики до и после.
